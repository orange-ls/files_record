学习路线 · 工程实践 · 可检验成果

Python 后端转 AI 应用开发
24 周学习规划

适用起点：熟悉 CRUD、问题定位和业务需求分析。目标：能设计、验证和交付一个小型 AI 后端服务。资料核对日期：2026-09-17。

方向：保留后端优势，补齐 AI 应用的可靠性

推荐先走“Python 后端＋AI 应用工程”，暂时不转向模型训练。你的后端经验可以直接用于 API、数据处理、访问控制和部署；新增的学习重点是：模型输出有不确定性时，怎样定义正确、衡量效果，并限制错误的影响。

这条路线不保证岗位需求或薪资增长。它的优点是技能可迁移：即使以后换模型或框架，异步调用、数据契约、测试、评测和成本控制仍然用得上。AI 也能协助这些工作；你的学习标准是能解释选择并验证结果，不是记住某个工具的操作步骤。

按每周 4 小时、24 周计算，总投入约 96 小时。每周只有 3 小时，就按相同顺序延长到约 32 周；每周有 5 小时，额外时间优先用来复测和补缺口。它是一轮学习项目，不是“半年达到高级工程师”的承诺。

整条路线只使用一个主项目：工单辅助服务。先对工单做分类、摘要和缺失信息提取，再根据一小份公开知识库提供带出处的建议。最终答案供人审核，不自动关闭工单、退款或修改生产数据。

项目范围与技术选择

数据限定为约 30 条人工编写或公开工单、20 篇短小的 Markdown/TXT 知识文档，不接入公司真实客户资料。只做 API，可以使用现有框架的接口文档页演示，不做独立前端。不要为了学习先建设完整工单系统。

沿用熟悉的 Python Web 框架；没有固定框架时可选 FastAPI。使用 Pydantic 定义数据结构、pytest 编写测试，先接入一个能合法访问且预算可控的模型 API。元数据用熟悉的关系数据库；小型检索实验可以先用内存向量索引，不必引入专用向量数据库。

SDK、异步接口和结构化输出支持情况以所选服务商与模型的当前文档为准。不要把“兼容某类 API”理解为所有功能完全一致。不为这份规划默认购买服务或申请付费资源。

六个阶段：学什么、做到什么程度

第 1—4 周：Python 工程补强，约 16 小时

学习阻塞 I/O 与异步 I/O 的区别、超时和取消、HTTP 客户端连接复用、Pydantic 校验，以及 pytest fixture 和 mock。补一点接口与数据库边界：不要把慢模型请求放在长数据库事务里等待，明确任务失败时状态如何更新。无需重学 CRUD，也不从头刷完 Python 教程。

在项目里写一个假的模型适配器，模拟成功、慢响应和非法响应。业务逻辑通过适配器调用模型，不直接散落在路由里。演示两个请求为什么可能互相阻塞，再修正它。

验收：成功、超时、非法响应至少各有一个可重复运行的测试；能说明资源何时创建和关闭。知道协程取消不代表远端请求已停止，也不代表同步线程一定结束。已经掌握的部分用实验直接验收，把时间留给后续阶段。

第 5—8 周：直接调用模型，约 16 小时

学习 token、上下文与输出预算，系统指令和用户输入的区分，JSON 与 JSON Schema 的差别，以及模型拒绝、输出截断和异常响应。先用官方 SDK 直接调用，不先引入编排框架。

实现工单分类、摘要、缺失信息提取，返回固定的数据结构。没有依据的字段允许为空，不让模型补造订单号或处理结论。设置输入长度和输出预算；核实 SDK 是否自带重试，避免外层重试叠加。只对适合重试的暂时性错误做有上限的重试，参数错误应直接处理。

验收：接口可以处理正常输入、空输入、超长输入、拒绝或非法输出，并返回可解释的状态。能说明“Schema 合法”只说明格式符合约定，不说明摘要事实正确。保留人工复核入口。

第 9—12 周：先评测，再调优，约 16 小时

学习评价标准、开发集与留出测试集、错误分类、实验变量控制，以及质量、延迟和调用费用的取舍。约 30 条样例中，20 条用于开发，10 条暂时留出；每条写清期望类别和摘要必须保留的事实。样本很小，只用于学习和发现问题，不据此推断生产准确率。

比较一个简单关键词分类基线与模型方案。建立脚本，记录格式有效性、分类是否正确、摘要是否捏造事实、延迟和可获得的 token 用量。失败、超时和重试也纳入统计。费用按服务商实际计价口径核算，不能把 token 总数乘以一个未经核对的单价。

验收：同一组样例能重复评测；改提示词时能指出哪些案例变好、哪些变坏，而不是挑几条好答案展示。10 条留出样例在一次阶段比较后再查看；用它们指导修改后，应补充新样例供下次独立检查。

第 13—16 周：做最小 RAG，约 16 小时

学习文本分块、embedding（向量表示）、相似度检索、Top-K 和证据引用。RAG 是先找出相关资料，再把资料交给模型回答；它不是训练模型，也不会自动消除事实错误。

为同一项目增加 20 篇短文档，保留文档 ID 和段落 ID。先建立简单关键词检索基线，再做小型向量检索。根据工单取回少量候选段落，再生成带引用的处理建议。资料不足时，返回“证据不足，需人工确认”。

验收：可以查看每个问题实际命中的段落和最终引用；能指出失败发生在检索还是生成。引用 ID 必须真实存在，但 ID 存在仍不代表证据支持答案，需要人工核对。不做 PDF/OCR、爬虫、复杂文档解析或混合检索平台。

第 17—20 周：RAG 评测与安全边界，约 16 小时

为约 20 个知识问答标注应命中的证据，覆盖能回答、知识库里没有答案、表述含糊的情况。分开记录证据是否进入候选、答案是否有依据、无答案时是否合理拒答。阈值从自己的样例观察，不照搬别人使用的固定相似度分数。

只改变一个变量，比较分块或 Top-K 的效果。加入一条包含“忽略先前规则”等无害测试文字的文档，观察模型是否把资料当指令。文档内容是不可信输入；程序中限制数据范围、输出字段和可执行操作，不依赖一段提示词充当安全边界。

验收：能展示一次检索改动的得失，以及一次无依据回答如何被发现。若以后扩展多用户，必须在检索和工具执行的服务端检查权限，不能把所有文档都发给模型后再要求它“不要泄露”。这一阶段不承诺解决全部提示注入问题。

第 21—24 周：交付、取舍与作品说明，约 16 小时

补齐运行配置、依赖锁定、请求 ID、错误日志和基本调用量记录。日志避免记录密钥和完整敏感输入。在干净的本地环境或容器里运行，模拟上游不可用，确认应用能够失败返回并恢复；不必公开部署到互联网。

整理一页设计说明，解释为什么采用当前框架、为什么不拆微服务、如何在质量与费用间取舍。记录模型或提示词配置版本，做一次配置回退演练。让一位同事或朋友使用合成数据试用，留下反馈与修正记录。

验收：别人能按说明运行；你能展示测试、评测对比和已知不足；同一个失败案例从日志可以追到处理结果。能说明哪些场景适用普通规则、直接模型调用或 RAG，以及当前方案不适合什么。完成的是可评审的学习作品，不是生产就绪认证。

双周任务表

周次只交付这一件东西检查方式
1—2最小接口和假的模型适配器；一次阻塞/异步对比实验。解释等待发生在哪里，不只比较代码长短。
3—4成功、超时、非法输出测试；资源生命周期处理。离线运行测试，不需要真实 API Key。
5—6用一个真实模型完成结构化工单提取。校验输出字段，核对事实；不确定项保留为空。
7—8输入/输出预算和有上限的失败处理。模拟空输入、上游报错和截断，检查返回状态。
9—1030 条带标准的样例与一个简单分类基线。区分20条开发样例与10条留出样例。
11—12一次单变量提示词实验及评测记录。同时记录退步案例、失败次数和调用成本。
13—1420 篇纯文本知识文档及可查看的检索结果。保留来源 ID，比较关键词与向量检索。
15—16带引用的知识建议接口。对照引用核实答案，资料不足时不强行回答。
17—18约20个知识问答的检索/生成分项评测。一次只改分块或Top-K，不同时修改全部变量。
19—20失败案例与数据边界测试。覆盖资料中的误导指令；确认没有自动写入动作。
21—22可复现运行、日志与上游故障演练。在另一套干净环境或容器中验证。
23—24设计说明、评测结果、试用反馈与最终演示。解释取舍与不足，让他人提问并复核。

每周怎么学，才不会变成教程收藏

每周约 60 分钟读当前任务需要的文档，120 分钟实现和实验，30 分钟检查失败样例，30 分钟写下本周结论。笔记只回答几个具体问题：我原来以为怎样，实验发生了什么，下一次改什么。忙的一周沿用原任务，不同时启动新课程。

系统性来自知识之间的联系。例如，模型请求慢，涉及网络等待、超时和并发；答案错，涉及数据证据、任务定义和评测；费用高，涉及调用次数与输入输出预算。把每个知识点用在同一个系统里，比同时学习六个框架更能形成理解。

AI 可以解释陌生代码、提出测试用例、检查小段改动。设计预期结果后再请它实现，不让生成代码的同一套假设决定全部验收标准。每个阶段至少独立解释一次关键调用链，并亲自定位一个注入的失败。参考答案、官方文档和实际运行结果要相互核对。

现在就做的第一步：用合成工单确定“分类、摘要、缺失信息”三个输出字段，写 5 条输入与期望结果，然后实现一个不调用真实模型的适配器。第一周先把这个小闭环跑通，不购买大课，不搭建完整 AI 平台。

暂缓什么，后续再选什么

本轮暂缓从零训练模型、系统性微调、多 Agent、复杂工作流平台、Kubernetes、大规模分布式架构，以及完整线性代数和深度学习课程。你需要先理解向量相似度、token 和评测这些会直接用到的概念，但不必先推导 Transformer 才能做应用。算法和计算机基础不是没有用；在求职或项目出现明确缺口时，再安排专项投入。

完成本轮后，再挑一个方向投入后续约 8 周。如果知识问答最有价值，继续研究检索评测、重排与文档更新；如果系统需要查询业务状态，学习受限的只读工具调用，理解 Schema 校验、服务端授权、超时和人工确认；如果更喜欢后端工程，深入数据库事务、任务队列、负载测试与可观测性。先选一条，不把所有方向同时加入下一轮。

LangChain 等框架、工作流工具和 MCP 可以在出现具体集成需求后学习。MCP 是连接工具和数据的协议层，不代替模型能力、权限设计或评测。不以会多少框架作为学习成绩。

学习资料：按章节查，不从头刷完

Python：Coroutines and Tasks。用于第1阶段，重点看任务、超时、取消和在异步代码中处理阻塞调用；按自己使用的Python版本核对接口。

FastAPI 官方文档与异步测试。用于请求体校验、lifespan与测试。若项目使用Django或Flask，沿用原框架对应的官方文档，不为教程迁移。

pytest：Fixtures。用于可重复的测试准备与清理；从本项目用例学习，不学习插件开发。

百炼：结构化输出。用于理解JSON Object和JSON Schema的差异。它是一个可选服务商的官方示例，不是指定采购；能力随模型和模式而异。

百炼：RAG效果优化。用于检索结果、文档分块和生成效果的分开检查。文中的平台配置不是自行实现RAG时的强制组件。

百炼：应用评测。作为后续平台评测入口参考；本轮先用Python脚本和人工标注，不要求开通平台功能。

这份规划依据你提供的学习起点、Python技术栈和每周时间制定。时间与样本规模是学习安排，不是行业标准；每个阶段以验收结果决定是否进入下一阶段。公开文档可能更新，实际接入时重新核对API能力、计费和数据使用条款。

# spec 模式规范（强制执行）

> ⚠️ 这是一条强制规则，不允许跳过或变通。spec 目录必须严格基于 git 分支名解析生成，禁止使用自拟名称。当使用 spec 模式进行项目开发时适用该规则，其他场景不适用该规则。

## 分支命名规范

团队约定分支命名格式为 `{modulename}_{版本号}`，其中：
- `modulename`：模块名称，如 `xc_app`、`xc_borrow`、`xc_dboms`
- `版本号`：语义化版本号，格式为 `X.Y.Z`（如 `1.0.2`、`1.2.6`、`2.5.18`）

合法分支名示例：`xc_app_1.0.2`、`xc_borrow_1.2.6`、`xc_dboms_2.5.18`

## 目录结构

specs 模式下创建的文档按模块名 + 版本号两层目录组织：

```
.kiro/specs/{modulename}/{版本号}/
```

以分支 `xc_borrow_1.2.6` 为例，最终目录为：`.kiro/specs/xc_borrow/1.2.6/`

## 执行步骤（必须严格按顺序执行）：

1. **第一步（必须）**：在启动 spec 模式之前，先确认当前 git 分支是否合理正确，不正确的话禁止执行任务。
2. **第二步（必须）**：运行 `git rev-parse --abbrev-ref HEAD` 获取当前分支名
3. **第三步（必须）**：校验分支名格式是否符合 `{modulename}_{X.Y.Z}` 规范（正则：`^[a-z][a-z0-9_]*_\d+\.\d+\.\d+$`）。如果不符合，向用户报错并禁止继续执行，提示用户切换到符合规范的分支。
4. **第四步（必须）**：从分支名中解析出模块名和版本号。解析规则：以最后一个 `_` 为分隔符，左侧为 `modulename`，右侧为版本号。例如 `xc_borrow_1.2.6` → 模块名 `xc_borrow`，版本号 `1.2.6`
5. **第五步（必须）**：向用户确认当前分支是否正确（例如："当前分支为 `xc_borrow_1.2.6`，模块名 `xc_borrow`，版本号 `1.2.6`，确认在此分支上进行开发吗？"）
6. **第六步（必须）**：创建 spec 目录。先检查 `.kiro/specs/{modulename}/` 目录是否已存在：
   - **已存在**（同模块的历史版本已创建过该目录）：无需重复创建模块名目录，直接在其下新建版本号子目录 `{版本号}/` 即可
   - **不存在**（该模块首次创建 spec）：先创建模块名目录 `{modulename}/`，再在其下创建版本号子目录 `{版本号}/`
   
   在最终的 `.kiro/specs/{modulename}/{版本号}/` 目录下创建或存放本次开发的所有 spec 文件
7. **第七步（检查）**：如果发现本次开发相关的 spec 文件不在正确的目录下，将其移动到当前分支对应的目录中

## 严格禁止事项：
- ❌ 禁止自行命名 spec 目录（如用功能名、完整分支名等代替模块名+版本号两层结构）
- ❌ 禁止跳过获取分支名和格式校验的步骤
- ❌ 禁止将不同分支的 spec 文件混放在同一目录下，或者随意迁移
- ❌ 禁止在未获取分支名的情况下创建 spec 目录
- ❌ 禁止在 `main`、`master`、`develop` 等主干分支上直接进行开发（需提醒用户切换到功能分支或者创建新分支）
- ❌ 禁止使用不符合 `{modulename}_{X.Y.Z}` 格式的分支进行 spec 开发
- ❌ 禁止将 spec 文件放在单层目录下（如 `.kiro/specs/xc_borrow_1.2.6/`），必须使用两层结构
- ❌ 禁止在模块名目录已存在时重复创建，应直接复用

## 正确示例：
- 分支名 `xc_app_1.0.2` → 目录 `.kiro/specs/xc_app/1.0.2/`
- 分支名 `xc_borrow_1.2.6` → 目录 `.kiro/specs/xc_borrow/1.2.6/`
- 分支名 `xc_dboms_2.5.18` → 目录 `.kiro/specs/xc_dboms/2.5.18/`
- 同模块迭代：已有 `.kiro/specs/xc_borrow/1.0.0/`，新分支 `xc_borrow_1.1.0` → 直接创建 `.kiro/specs/xc_borrow/1.1.0/`，复用已有的 `xc_borrow/` 目录

## 错误示例：
- 分支名是 `xc_borrow_1.2.6`，但目录创建为 `.kiro/specs/xc_borrow_1.2.6/` ← ❌ 单层目录，缺少版本号子目录
- 分支名是 `xc_borrow_1.2.6`，但目录创建为 `.kiro/specs/borrow/1.2.6/` ← ❌ 模块名不正确
- 分支名是 `feature/add-login` ← ❌ 分支名不符合命名规范，禁止执行

## 注意事项：
- 同一模块的不同版本 spec 自然按版本号子目录隔离，如 `.kiro/specs/xc_borrow/1.0.3/` 和 `.kiro/specs/xc_borrow/1.2.6/`
- 已有版本目录中的 spec 文件不要随意删除，作为历史版本保留
- 切换分支后如需创建新 spec，必须重新解析分支名并在对应的模块名/版本号目录下创建

## 总 requirements.md 同步规范（强制执行）

> ⚠️ 每次 spec 模式开发完成（所有 tasks 执行完毕）后，必须将当前版本的需求同步合并到模块的总需求文档中。

### 目录与文件

总需求文档存放路径：

```
.kiro/specs/{modulename}/backup/requirements.md
```

该文件是模块的**活文档**，格式与 kiro spec 生成的 requirements.md 完全一致（标题 + 简介 + 术语表 + 需求列表），是所有版本需求合并后的完整最新状态，可直接作为迁移需求文档交给 kiro 执行。

### 同步时机

当 spec 模式下所有 tasks 执行完毕后（即开发完成时），必须执行同步操作。

### 需求编号规则

总文档中的需求编号全局唯一、单调递增，不与任何版本的局部编号重复：

- **首次同步**：直接沿用当前版本的编号（如 需求 1、需求 2...需求 N）
- **新增需求合并**：读取总文档中当前最大需求编号 `MAX_N`，新版本中新增的需求从 `MAX_N + 1` 开始重新编号后再合并进总文档
- **编号映射记录**：合并时在需求标题后用注释标注来源版本和原始编号，格式为 `<!-- 来源: v{版本号} 原编号: 需求{N} -->`，便于追溯
- **变更/删除需求**：保持总文档中已有的编号不变，就地更新或删除对应条目

### 同步规则

1. **首次同步**：`backup/requirements.md` 不存在时，直接将当前版本的 requirements.md 完整内容复制过去，各需求标题后追加来源注释 `<!-- 来源: v{版本号} 原编号: 需求{N} -->`
2. **新增需求**：读取总文档最大编号，新需求从 `MAX_N + 1` 递增编号，追加来源注释后合并到总文档末尾（需求列表部分）
3. **需求变更**：在总文档中找到对应条目（通过来源注释或语义匹配），就地更新内容，保持总文档编号不变，更新来源注释中的版本号
4. **功能删除**：从总文档中删除对应的需求条目，同步清理术语表中相关术语
5. **简介/术语表更新**：如当前版本的简介或术语表有变化，同步更新总文档的对应部分
6. **禁止堆叠**：禁止将整个版本的 requirements.md 原文追加到总文档末尾，总文档始终是一份完整的、可直接执行的需求文档

### 总文件格式示例

```markdown
# 需求文档：{模块功能名称}

## 简介

{模块功能的整体描述，反映当前最新状态}

## 术语表

- **{术语}**：{定义}

## 需求

### 需求 1：{需求标题} <!-- 来源: v1.0.0 原编号: 需求1 -->

**用户故事：** 作为{角色}，我希望{目标}，以便{价值}。

#### 验收标准

1. THE {System} SHALL {条件}
2. WHEN {触发条件} THE {System} SHALL {行为}

### 需求 2：{需求标题} <!-- 来源: v1.0.0 原编号: 需求2 -->

...

### 需求 11：{新版本新增需求标题} <!-- 来源: v1.1.0 原编号: 需求1 -->

**用户故事：** ...

#### 验收标准

1. ...
```

### 执行步骤

在 spec 开发完成后，agent 必须执行以下步骤：

1. 检查 `.kiro/specs/{modulename}/backup/` 目录是否存在，不存在则创建
2. 检查 `backup/requirements.md` 是否存在：
   - **不存在**：将当前版本 requirements.md 完整内容复制为 `backup/requirements.md`，为每条需求标题追加来源注释
   - **已存在**：读取总文档，扫描当前最大需求编号 `MAX_N`；读取当前版本 requirements.md，识别新增/变更/删除的需求，新增需求从 `MAX_N + 1` 递增编号后合并，变更需求就地更新，删除需求直接移除
3. 向用户确认同步完成，说明本次合并了哪些变更（新增/更新/删除了哪些需求，新编号范围）

# Vibe 模式工作规范（强制执行）

> ⚠️ 这是一条强制规则。使用 vibe 模式（即直接在聊天中）对现有模块进行需求级变更时，必须严格遵守以下规范。

## 适用范围

本规范仅适用于 vibe 模式下的需求级变更，即需求本身发生了变化的场景，且本次任务处理的是 xc_addons 下的文件：
- **需求变更**：原有需求描述不准确、需求理解有误、实际功能与需求不符需要修正需求
- **功能优化**：对已有功能的改进，涉及需求层面的调整
- **功能增补**：原 spec 中未覆盖的新增小功能

以下场景不适用本规范，遵循 `development_rules.md` 即可：
- Bug 修复（需求没问题，只是代码实现有缺陷）
- 重构（不改变功能行为的代码结构调整）

## 执行步骤（必须严格按顺序执行）：

1. **第一步（必须）**：使用vibe处理用户任务之前，先确认当前 git 分支是否合理正确，不正确的话禁止执行任务
2. **第二步（必须）**：运行 `git rev-parse --abbrev-ref HEAD` 获取当前分支名
3. **第三步（必须）**：校验分支名格式是否符合 `{modulename}_{X.Y.Z}` 规范（正则：`^[a-z][a-z0-9_]*_\d+\.\d+\.\d+`）。如果不符合，向用户报错并禁止继续执行，提示用户切换到符合规范的分支。
4. **第四步（必须）**：从分支名中解析出模块名和版本号。解析规则：以最后一个 `_` 为分隔符，左侧为 `modulename`，右侧为版本号。例如 `xc_borrow_1.2.6` → 模块名 `xc_borrow`，版本号 `1.2.6`
5. **第五步（必须）**：向用户确认当前分支是否正确
6. **第六步（必须）**：检查当前分支是否已有对应的 spec 目录（`.kiro/specs/{modulename}/{版本号}/`），根据结果走不同路径：
   - **情况一：spec 目录已存在**（同版本迭代）→ 读取现有的 `requirements.md`、`design.md`、`tasks.md`、`traceability-matrix.md`
   - **情况二：spec 目录不存在**（新版本迭代）→ 标记为"需新建 spec"，编码完成后创建轻量版 spec 文件

7. **第七步（必须）**：编码过程中严格遵循 `develop_code_traceability` 技能中的代码标注规范：
   - **情况一（已有 spec）**：关联已有需求编号使用已有的 `@requirement` 和 `@task` 标注；新增需求则在现有最大编号基础上递增
   - **情况二（新建 spec）**：需求编号从 `{modulename}_{版本号}-REQ-1` 开始，任务编号从 `{modulename}_{版本号}-TASK-1` 开始
   - 多版本迭代标注规则同样适用：在已有函数上追加新的 `@requirement` / `@task`，保留历史标注

### 情况一：已有 spec 目录 → 追加更新

#### 8.1 更新 requirements.md

- **需求变更**：修改已有需求条目或验收标准，使其与实际功能一致。在修改处添加 `[VIBE-{日期}]` 标记，说明变更原因
- **功能优化**：在已有需求下追加新的验收标准，或修改现有验收标准。使用 `[VIBE-{日期}]` 标记
- **功能增补**：追加新的需求条目，使用 `[VIBE-{日期}]` 前缀标记来源

#### 8.2 更新 design.md（仅在涉及设计变更时）

以下情况需要更新 design.md：
- 新增或修改了模型字段
- 新增或修改了 API 接口
- 修改了错误处理策略
- 修改了安全/权限设计

在对应章节追加或修改内容，并添加 `<!-- vibe: {日期} {简要说明} -->` 注释标记变更来源。

#### 8.3 更新 tasks.md

在 tasks.md 末尾追加 vibe 模式产生的任务记录，使用独立的 `## Vibe 迭代任务` 章节，与原始 spec 任务区分：

```markdown
## Vibe 迭代任务

- [x] V1. [{日期}] {任务简述}（{类型：功能优化/需求变更/功能增补}）
  - 关联需求：REQ-{编号}
  - 变更文件：
    - `{文件路径}` — {修改说明}
  - _需求: {关联的需求编号列表}_
```

任务编号使用 `V{序号}` 格式（V 代表 Vibe），避免与原始 spec 任务编号冲突。

#### 8.4 更新 traceability-matrix.md

在追溯矩阵表格中追加本次变更的记录，变更类型使用对应的标记：

| 变更类型 | 标记 |
|----------|------|
| 功能优化 | 优化 |
| 需求变更 | 变更 |
| 功能增补 | 新增 |

同时更新矩阵头部的"更新日期"字段。


### 情况二：新分支无 spec 目录 → 创建轻量版 spec

在 `.kiro/specs/{modulename}/{版本号}/` 下新建轻量版 spec 文件，内容精简但符合规范：

#### 8.5 创建轻量版 requirements.md

```markdown
# 需求文档：{模块中文名}（{module_name}）— Vibe 迭代版本

> 基于分支 `{branch_name}` 的 Vibe 模式迭代，轻量版需求记录。

## 迭代背景

- 基线分支：{从哪个分支派生，如 xc_borrow_1.0.0}
- 基线 spec：`.kiro/specs/{基线模块名}/{基线版本号}/`
- 迭代类型：Vibe 小版本迭代

## 需求

### 需求 1：{需求简述} [VIBE-{日期}]

**用户故事：** 作为{角色}，我希望{目标}，以便{价值}。

#### 验收标准
1. ...
```

关键点：
- 标注基线分支和基线 spec 路径，建立版本间的关联
- 需求编号从 1 开始独立编号
- 每条需求带 `[VIBE-{日期}]` 标记

#### 8.6 创建轻量版 tasks.md

```markdown
# 实施任务：{模块中文名}（{module_name}）— Vibe 迭代版本

> 基于分支 `{branch_name}` 的 Vibe 模式迭代任务记录。

## 迭代背景

- 基线分支：{基线分支名}
- 基线 spec：`.kiro/specs/{基线模块名}/{基线版本号}/`

## 任务

- [x] 1. [{日期}] {任务简述}
  - 变更文件：
    - `{文件路径}` — {修改说明}
  - _需求: 1_
```

#### 8.7 创建轻量版 traceability-matrix.md

```markdown
# 需求 → 代码追溯矩阵

## 模块信息
- 模块名称：{module_name}
- 分支名称：{branch_name}
- 基线分支：{基线分支名}
- 更新日期：{日期}

## 追溯记录

| 需求ID | 任务ID | 实现文件 | 函数/类 | 变更类型 | 说明 |
|--------|--------|----------|---------|----------|------|
| REQ-1 | TASK-1 | {文件路径} | {函数/类名} | 新增 | {说明} |
```

#### 8.8 design.md（可选）

轻量版迭代中，仅在涉及模型字段变更、API 接口变更、权限变更等设计层面改动时才创建 design.md。若仅是简单的功能增补且不涉及设计变更，可不创建。

## 代码变更执行规范

### 修改前：
- 阅读并理解待修改文件的现有代码逻辑
- 如果涉及模型字段变更，检查是否有其他模块依赖该字段
- 如果涉及 API 接口变更，检查是否有前端或外部系统调用
- 读取当前分支的 spec 文件，确认本次变更关联的需求编号

### 修改中：
- 遵循 `development_rules.md` 中的所有开发规则
- 遵循 `develop_code_traceability` 技能中的代码标注规范（`@requirement`、`@task`、`@businessRule` 等）
- 关键变更处添加 `# vibe: {简要说明}` 标记，便于后续 code review

## 严格禁止事项
- ❌ 禁止跳过分支确认步骤直接修改代码
- ❌ 禁止在 `main`、`master`、`develop` 等主干分支上直接进行开发
- ❌ 禁止未确认分支就开始修改代码
- ❌ 禁止需求级变更不更新 spec 文件
- ❌ 禁止需求级变更代码中不添加 `@requirement` / `@task` 追溯标注
- ❌ 禁止修改 `addons/` 或 `odoo/` 目录下的核心框架文件
- ❌ 禁止在 vibe 模式下进行大规模架构重构（应使用 specs 模式）
- ❌ 禁止跨分支混合修改（一次 vibe 会话只能在一个分支上操作）
- ❌ 禁止删除已有的 `@requirement` / `@task` 历史标注

## 何时应切换到 Specs 模式

以下情况建议用户切换到 specs 模式，而非使用 vibe 模式：
- 新增完整功能模块（需要新建模块目录）
- 涉及 3 个以上模块的联动变更
- 需要新增数据模型或大幅修改现有模型结构
- 需要团队评审的重大架构变更

## 总 requirements.md 同步规范（强制执行）

> ⚠️ 每次 vibe 模式下的需求级变更完成后，必须将当前版本的需求同步合并到模块的总需求文档中。

### 目录与文件

总需求文档存放路径：

```
.kiro/specs/{modulename}/backup/requirements.md
```

该文件是模块的**活文档**，格式与 kiro spec 生成的 requirements.md 完全一致（标题 + 简介 + 术语表 + 需求列表），是所有版本需求合并后的完整最新状态，可直接作为迁移需求文档交给 kiro 执行。

### 同步时机

当 vibe 模式下需求级变更完成后（代码修改 + spec 文件更新均完成），必须执行同步操作：
- 情况一（已有 spec 目录）：更新完 requirements.md 等 spec 文件后，将变更同步合并到总文档
- 情况二（新建 spec 目录）：创建完轻量版 spec 文件后，将新需求合并到总文档

### 需求编号规则

总文档中的需求编号全局唯一、单调递增，不与任何版本的局部编号重复：

- **首次同步**：直接沿用当前版本的编号（如 需求 1、需求 2...需求 N）
- **新增需求合并**：读取总文档中当前最大需求编号 `MAX_N`，新版本中新增的需求从 `MAX_N + 1` 开始重新编号后再合并进总文档
- **编号映射记录**：合并时在需求标题后用注释标注来源版本和原始编号，格式为 `<!-- 来源: v{版本号} 原编号: 需求{N} -->`，便于追溯
- **变更/删除需求**：保持总文档中已有的编号不变，就地更新或删除对应条目

### 同步规则

1. **首次同步**：`backup/requirements.md` 不存在时，直接将当前版本的 requirements.md 完整内容复制过去，为每条需求标题追加来源注释 `<!-- 来源: v{版本号} 原编号: 需求{N} -->`
2. **新增需求**：读取总文档最大编号，新需求从 `MAX_N + 1` 递增编号，追加来源注释后合并到总文档末尾（需求列表部分）
3. **需求变更**：在总文档中找到对应条目（通过来源注释或语义匹配），就地更新内容，保持总文档编号不变，更新来源注释中的版本号
4. **功能删除**：从总文档中删除对应的需求条目，同步清理术语表中相关术语
5. **简介/术语表更新**：如当前版本的简介或术语表有变化，同步更新总文档的对应部分
6. **禁止堆叠**：禁止将整个版本的 requirements.md 原文追加到总文档末尾，总文档始终是一份完整的、可直接执行的需求文档

### 总文件格式示例

```markdown
# 需求文档：{模块功能名称}

## 简介

{模块功能的整体描述，反映当前最新状态}

## 术语表

- **{术语}**：{定义}

## 需求

### 需求 1：{需求标题} <!-- 来源: v1.0.0 原编号: 需求1 -->

**用户故事：** 作为{角色}，我希望{目标}，以便{价值}。

#### 验收标准

1. THE {System} SHALL {条件}
2. WHEN {触发条件} THE {System} SHALL {行为}

### 需求 2：{需求标题} <!-- 来源: v1.0.0 原编号: 需求2 -->

...

### 需求 11：{新版本新增需求标题} <!-- 来源: v1.1.0 原编号: 需求1 -->

**用户故事：** ...

#### 验收标准

1. ...
```

### 执行步骤

在 vibe 模式需求级变更完成后，agent 必须执行以下步骤：

1. 检查 `.kiro/specs/{modulename}/backup/` 目录是否存在，不存在则创建
2. 检查 `backup/requirements.md` 是否存在：
   - **不存在**：将当前版本 requirements.md 完整内容复制为 `backup/requirements.md`，为每条需求标题追加来源注释
   - **已存在**：读取总文档，扫描当前最大需求编号 `MAX_N`；读取当前版本 requirements.md，识别新增/变更/删除的需求，新增需求从 `MAX_N + 1` 递增编号后合并，变更需求就地更新，删除需求直接移除
3. 向用户确认同步完成，说明本次合并了哪些变更（新增/更新/删除了哪些需求，新编号范围）
